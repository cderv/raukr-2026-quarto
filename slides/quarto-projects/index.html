Part 1 — Build & structure a project

From one file to a whole site.

Why a project?

Follow along

Open your editor: from here we build one project together.

One .qmd renders alone. A project is a folder Quarto treats as one unit (shared config, one build, one output folder):

_quarto.yml
# at the project root
project:
  type: website
  output-dir: _site  # everything renders here
format:
  html:
    toc: true          # set once, every page gets it
  • quarto render builds the whole folder, not one file.
  • Header options set once apply to every page.
  • output-dir — the folder the built site lands in (_site by default). Publish that.
  • Say: “Day 1 was one file. Today: many files, one project. Open your editor — we build one together.”
  • Do: show a minimal _quarto.yml — project: type: website + output-dir. “This folder is now one unit; render builds all of it, not one file.”
  • Say (relevance): the team project is many pages — this is how they connect.

Quarto uses the nearest _quarto.yml up the tree as the project root: you add one to day2-projects/, and nothing sits above it, so that folder is your project.

Directory metadata — _metadata.yml

Yesterday a header set the defaults and a cell overrode them. _metadata.yml is that same idea, one scope wider: options for every page in a folder, so you don’t repeat them in each header:

analysis/_metadata.yml
# applies to every .qmd in analysis/
execute:
  echo: false
  warning: false
format:
  html:
    code-fold: true

Same narrow-wins rule, now across files: document header > _metadata.yml > _quarto.yml. Set defaults wide, override narrow.

  • Callback (don’t re-teach): they learned header-vs-cell precedence yesterday (#execution). Don’t re-derive “defaults wide, override narrow” — just widen it to the file/folder/project scope.
  • Say: “Same rule as yesterday’s header-beats-nothing / cell-beats-header — now a folder file sits between the page and the project.”

Today’s lab project is flat (a couple of pages at the root), so there’s no folder to scope. Reach for _metadata.yml when a subfolder of pages shares options.

Websites — pages & navigation

You already set type: website, which makes the folder a site: its pages share one navbar and sidebar. You describe that navigation once, and Quarto builds it:

_quarto.yml
website:
  title: "Penguin Lab"
  # top bar — one entry per page
  navbar:
    left:
      - href: index.qmd
        text: Home
      - href: analysis.qmd
        text: Analysis
  # side menu, built from the files
  sidebar:
    contents: auto

contents: auto even builds the sidebar from the folder, so you don’t hand-list pages.

  • Do: add the website: block live — navbar + sidebar — render, show the nav appear.
  • Say: “You declare the nav once: the navbar you list, the sidebar contents: auto builds from the files — Quarto generates both.”
  • Say (sets up next slide): “each page renders on its own — that independence is exactly why cross-refs behave differently across pages.”
  • Helpers: flag the classic trap now — links are relative to the source, not _site — so they meet it before the lab.

Listings turn a folder of pages into an auto-generated index (a blog, a gallery of reports) via listing: on a page. One slide’s worth, more in the linked resources.

Project-wide numbering is a book

If you need “Figure 3.2” to resolve across chapters, that’s type: book: Quarto renders a book as one unit with global numbering. A website keeps per-page numbering.

One brand → the whole project: _brand.yml

Yesterday, _brand.yml branded one Typst PDF. Drop that same file at the project root and Quarto auto-discovers it (no header line, no per-page config):

_brand.yml
color:
  palette:
    teal: "#4C979F"
  primary: teal
typography:
  fonts:
    - family: Albert Sans
      source: google
  base:
    family: Albert Sans
  • Every page and every deck inherits it from that one root file, so you never name it in a page.
  • Add a page tomorrow? Branded on render, nothing to wire up.
  • Need an exception? brand: false opts a page out; brand: other.yml points it elsewhere.
  • Callback (don’t re-derive): they saw this file yesterday, branding the PDF. Today’s new angle is scale — one root file themes the whole multi-page project. Widen the scope; don’t re-teach the file.
  • Hold back the theme-layer rule. It used to be an aside on this slide. It is now the lab’s brand step (Part 1, “Brand it”): they add _brand.yml, the fonts change, the colors don’t, and working out why is the exercise. Saying “brand goes last, later layers win” here turns that step back into transcription. If someone asks outright, answer with the question instead: “what order do you think Quarto puts them in?”
  • Do: show the site before / after dropping _brand.yml at the root — navbar + links go teal in one re-render. Check your demo project first: a bare theme: cosmo outranks the brand and the demo shows nothing. The theme list needs brand last (theme: [cosmo, brand]), or no theme: at all. Fix it silently before the session; don’t narrate the fix.
  • Say: “You saw this yesterday. Put it at the project root and every page and deck inherits it — brand once, not per file.”
  • R plots (only if asked): a plot still needs theme_brand_ggplot2() — same as yesterday; the lab’s stretch covers it.
  • Escape hatch (if asked): brand: false opts a page out; brand: other.yml points it elsewhere — the default brands everything, these are the overrides.
  • Precision: “every page/deck” = every supported-format output (html, revealjs, typst, dashboard); an unsupported format just isn’t branded — don’t say “every output”.
  • Placement: this is Part-1 project config, not the Part-2 tail.
  • Helpers: the lab installs brand.yml with install.packages() (not pak).

Freeze — don’t re-run the slow stuff

Follow along

Back in your project’s _quarto.yml.

Day 1 I teased freeze: here’s the full story. Compute can be slow: you don’t want every prose edit to re-run a 20-minute model fit. Two tools, easily confused:

  • cache — the compute engine’s cache, not Quarto’s: it defers to knitr (R) / Jupyter Cache. Per-cell, kept until that cell’s code changes, and it works in a single document.
  • freeze — Quarto’s own switch, not about compute: it sets when a document re-executes. Project-only: rendering one file always runs it. Results live in _freeze/, refreshed only when its source changes. Commit it and CI (the automated build) rebuilds with no R at all.
# _quarto.yml
execute:
  freeze: auto        # re-execute a document only when its source changes

That’s freeze: auto, the setting to adopt: a page re-runs only when its own source changes. freeze: true hands you full control instead → next slide.

  • Say (motivation): “Compute can be slow — you don’t want a prose typo to re-run a 20-minute model fit.” (Localize to the room: a sequence alignment, a long MCMC, a big simulation.)
  • Do: the contrast is the point — cache = the engine’s cache (knitr for R / Jupyter Cache), per-cell, works in a single doc; freeze = Quarto’s switch, project-only, re-executes a doc only when its source changes. (Verified vs quarto.org docs/projects/code-execution.html.) Protect this distinction.
  • Do: show freeze: auto in _quarto.yml; “re-runs a page only when that page changed.”
  • If asked — why not just cache everything? cache is per-cell and can go stale across a shared repo; freeze commits whole-document results for reproducible, R-free CI rebuilds. Different jobs.
  • Say (payoff): commit _freeze/ and CI (a build that runs on every push) rebuilds the site with no R at all.
  • Teaser: the next slide is freeze: true — the render-on-demand workflow.

The freeze workflow — you hold the trigger

With freeze: true, a project build never runs R: it always reuses _freeze/. You refresh a page only when you choose to, by rendering that one file (a single-file render always executes):

_quarto.yml
execute:
  freeze: true
quarto render analysis.qmd     # runs the code, rewrites _freeze/ — commit it with your change

The loop: edit a page → render that one file → commit _freeze/. The project build and CI stay R-free: only the page you touched recomputes. That’s exactly how quarto.org itself is built.

freeze: auto instead lets the build recompute any changed (or not-yet-frozen) page. Convenient, but true keeps the trigger in your hands.

  • Anchor (real): quarto.org runs freeze: true — verified in quarto-dev/quarto-web/_quarto.yml; contributors render the changed file locally and commit _freeze/, enforced by a check-freeze.sh git hook — the same discipline this workshop repo uses.
  • Say: “true = the build never runs R; you decide when a page recomputes, by rendering it directly.”
  • Do: edit a cell on analysis.qmd → quarto render analysis.qmd → show _freeze/ change + the timestamp tick; a full project render leaves it untouched.
  • Contrast (lab uses auto): auto = the build recomputes changed pages for you (the setting you want, what the lab sets); true = deterministic CI + manual refresh (the CI mode).
  • If asked: a production render profile can set freeze: false to force a full re-execution.

Reproducibility has two parts

freeze pins the results. It doesn’t pin what produced them (the package versions):

  • freeze → _freeze/ — “don’t re-run the slow compute.”
  • renv.lock → “pin the packages, so the team rebuilds the same environment.”
renv::init()       # once, to start tracking
renv::snapshot()   # write renv.lock
renv::restore()    # rebuild the same env

Together: a colleague (or CI) rebuilds the same site, with or without re-running the analysis.

  • Timing: renv is the first thing to drop if short on time — the cache-vs-freeze contrast is the point of this beat, protect that.
  • Say: “freeze pins the results; renv.lock pins what produced them — the package versions. You want both.”

Publishing

The hands-on part is small: render, then point a host at output-dir.

quarto render              # builds the whole project into _site/
  • _site/ is the whole deliverable. Point any static host at it (an internal server, your department’s pages, a hosting service).
  • Posit Connect Cloud takes it in one command, with a free account and no repository:
quarto publish posit-connect-cloud

The first run opens a browser to sign in, then uploads the folder you just built.
