Part 1: Build and structure a project

From one file to a whole site.

Why a project?

A project is any folder that contains a _quarto.yml. That file gives you:

_quarto.yml
project:
  type: default
my-project/
|-- _quarto.yml   <- makes it a project
|-- index.qmd
|-- analysis.qmd
`-- reports/
  • One command for the whole folder: quarto render, no file argument.
  • One place for shared YAML, instead of the same header in every file.
  • One output folder you can publish.
  • freeze: a build can reuse stored results (Part 2).

type: selects the features Quarto adds. default is a plain folder of documents. website adds navigation. book treats the pages as one ordered document.

  • Say: “The four features above work for any type:.”
  • Do: run quarto create project to show the project types, then Ctrl-C. It would go on to create a folder.
  • Ask: “Which settings have you repeated in document headers so far?”
  • Watch for: quarto render in a folder with no _quarto.yml produces nothing and no error.
  • Next: we use website for the rest of the day.

Website or book?

Both build a browsable site. The question is how the pages are read:

type: Pick it when
website each page stands on its own. You get navigation, search, and listings. Today’s build.
book the pages read in order, as chapters, and you also want one PDF or EPUB.

quarto create project scaffolds either one and asks which type you want.

Learn more: Books

  • Say: “One type: line. Ordered chapters mean book, everything else means website.”
  • If asked: a blog is a website with a listing on its home page, not a third type.
  • If asked: the numbering consequence comes back on the cross-references slide.
  • Do not demo: we only point at books today.

Where the project starts

Quarto identifies the project root by searching up from the file being rendered and using the nearest _quarto.yml.

day2-projects/_quarto.yml
project:
  type: website
  output-dir: _site
format:
  html:
    toc: true
  • This is the nearest _quarto.yml, so day2-projects/ is the project root.
  • Everything under format: applies to every page in the project.
  • output-dir: where the built site is written. Publish that folder.

Nearest wins. Quarto ignores any _quarto.yml files above the project root.

  • Say: “Place _quarto.yml in a folder to make that folder the project root.”
  • Do: render once and show the output move from beside the .qmd into _site/.
  • Ask: “Where is the root if a folder above also has a _quarto.yml?” (The nearer _quarto.yml.)
  • Watch for: a project inside another project. Rendering from the outer folder builds the inner pages under the outer config.

Directory metadata: _metadata.yml

Yesterday a header set the defaults and a cell overrode them. _metadata.yml applies the same principle to every page in a folder, so you do not repeat the options in each header:

reports/_metadata.yml
# applies to every .qmd in reports/
execute:
  warning: false
format:
  html:
    code-fold: true

The same precedence rule now applies across files: document header > _metadata.yml > _quarto.yml. Set broad defaults, then override them at the document or folder level.

Learn more: Directory metadata

  • Say: “Same precedence rule as yesterday, now across project, folder, page, and cell.”
  • Do not re-teach: widen the rule only.

reports/ is the subfolder in today’s lab. Its options apply to the two pages inside it, not to the pages at the project root.

Websites: pages and navigation

type: website makes the folder a site. Define the navigation once in _quarto.yml, and Quarto applies it to every page.

_quarto.yml
website:
  title: "My Project"
  navbar:              # list the entries yourself
    left:
      - href: index.qmd
        text: Home
      - href: analysis.qmd
        text: Analysis
  sidebar:
    contents: auto     # or let Quarto derive them

With contents: auto, Quarto builds the sidebar from the folder structure. Each page’s title: becomes its label, each subfolder becomes a section, and pages appear alphabetically unless they set order:. New pages are included automatically.

Learn more: Websites · Listings

  • Do: quarto preview and show the navigation plus the built-in search.
  • Say: “Enumerate the navbar, derive the sidebar. Both live in one file.”
  • Next: independent pages explain the cross-reference rule.
  • Watch for: links are relative to source files, not _site.

Listings turn a folder of pages into an auto-generated index (a blog, a gallery of reports) via listing: on a page.

Cross-references across a project

Within one page, @fig-, @tbl-, @eq- resolve to a numbered, linked reference, exactly as on Day 1. Section headings work the same way with the @sec- prefix.

Across different website pages, they do not auto-number: a website renders each page on its own, so link between pages with ordinary Markdown links and the navbar/sidebar instead:

See the [analysis page](analysis.qmd) for the model.

Choose book for project-wide numbering

If you need “Figure 3.2” to resolve across chapters, that’s type: book: Quarto renders a book as one unit with global numbering. A website keeps per-page numbering.

One brand → the whole project: _brand.yml

Yesterday _brand.yml sat next to your report. At the project root, Quarto auto-discovers it for every page:

_brand.yml
color:
  palette:
    teal: "#4C979F"
  primary: teal
typography:
  fonts:
    - family: Albert Sans
      source: google
  base:
    family: Albert Sans
  • Every page and every deck inherits it from that one root file, so you never name it in a page.
  • Add a page later? Branded on render, nothing to wire up.
  • Need an exception? brand: false opts a page out. brand: other.yml points it elsewhere.

Learn more: Quarto brand · brand.yml spec

  • Say: it styled your HTML yesterday too, not only the PDF.
  • Do: show the site before/after adding _brand.yml.
  • Say: “Brand once at the project root, not once per page.”
  • Do not reveal: theme-layer order; it is the lab exercise.
  • Before session: demo uses [cosmo, brand] or no named theme.
  • If asked: plots need theme_brand_ggplot2(); brand: false opts out.
  • If asked (font changes, colors do not): a bare theme: cosmo expands to [brand, cosmo] and later layers win, so cosmo’s $primary replaces the brand color. The font arrives as --bs-body-font-family, which cosmo does not set, so it survives.

A real project configuration

The site you are reading this on is a Quarto project. It uses the same project: key, with two more entries:

_quarto.yml
project:
  type: website
  output-dir: _site
  brand:                    # one light, one dark
    light: _brand.yml
    dark: _brand-dark.yml
  render:                   # only these become pages
    - index.qmd
    - setup.qmd
    - slides/*/index.qmd
    - labs/*/index.qmd

render: limits which .qmd files Quarto renders. Without it Quarto renders every .qmd under the root. Prefix a file or directory name with _ to keep it out of the build: Quarto skips those by default. In a render: list, a leading ! removes a match. Put at least one positive include pattern before any exclusions. resources: copies files Quarto does not find on its own (a spreadsheet, a PDF) into _site/.

  • Say: “Nothing new here, just more of it. The real file is longer.”
  • Do: click the dark-mode toggle on this site to show where brand: lands.
  • If asked: render: is why the participant .qmd files in this repo are not site pages.
  • If asked: site search is on by default, so there is no key for it.

Freeze: skip unchanged computations

Computations can be slow: you do not want every prose edit to re-run a 20-minute model fit. Two tools are easy to confuse:

  • cache: the compute engine’s cache, not Quarto’s. It defers to knitr (R) or Jupyter Cache. Per-cell, kept until that cell’s code changes, and it works in a single document.
  • freeze: Quarto’s switch for when a document re-executes. Project-only: rendering one file always runs it. Results live in _freeze/. Once every page has frozen results, CI (the automated build) can rebuild those pages without R.
_quarto.yml
execute:
  freeze: auto

With freeze: auto, Quarto compares the page’s current source with the source recorded alongside its stored output. If the content is unchanged, Quarto reuses the output. If it changed, Quarto runs the code again. Re-saving an unchanged file does not trigger computation.

freeze is an ordinary option, so a _metadata.yml can set it for a single folder.

  • Say: “A prose edit should not rerun a 20-minute model.”
  • Contrast: cache = engine, per cell; freeze = Quarto, per document, project only.
  • Do: show _freeze/ on disk, one folder per page.
  • Payoff: commit _freeze/; CI can build without R.
  • Next: freeze: true gives manual control.

The freeze: true workflow

With freeze: true, a project build reuses _freeze/ even when the source changed. You refresh a page when you choose to, by rendering that one file (a single-file render always executes):

_quarto.yml
execute:
  freeze: true
quarto render analysis.qmd     # runs the code, rewrites _freeze/ — commit it with your change

With freeze: true, the workflow is: edit a page → render that one file → commit _freeze/. Once every page has been frozen, the project build and CI can reuse those results without R. This is how quarto.org is built.

freeze: auto instead lets the build recompute a page whose source changed. With true, you decide when to recompute each page.

  • Say: “With true, only a direct document render recomputes the page.”
  • Watch for: a page with no _freeze/ entry and a new page still execute.
  • If a render fails with cannot open file '<name>.qmd', delete the leftover <name>.knit.md or <name>.rmarkdown, then render again.
  • Contrast: auto recomputes changed pages; true requires manual refresh.
  • Example: quarto.org uses true and commits _freeze/.

Reproducibility has two parts

freeze pins the results. It doesn’t pin what produced them (the package versions):

  • freeze → _freeze/: do not repeat slow computation.
  • renv.lock → “pin the packages, so the team rebuilds the same environment.”
renv::init()       # once, to start tracking
renv::snapshot()   # write renv.lock
renv::restore()    # rebuild the same env

Together: a colleague (or CI) rebuilds the same site, with or without re-running the analysis.

Learn more: renv

  • Say: “freeze pins results; renv.lock pins package versions.”

One project, several builds

A profile is an overlay on _quarto.yml. The name comes from the file name, so _quarto-internal.yml is the internal profile:

_quarto-internal.yml
website:
  title: "Penguin Lab (internal)"
project:
  render:
    - "drafts/*.qmd"
quarto render --profile internal

Quarto reads _quarto.yml, then merges the profile on top. List entries are added, so this build is the usual pages plus the drafts.

Publishing

Publishing has two steps: render the project, then point a host at output-dir.

quarto render              # builds the whole project into _site/
  • _site/ is the whole deliverable. Point any static host at it (an internal server, your department’s pages, a hosting service).
  • Posit Connect Cloud takes it in one command, with a free account and no repository:
quarto publish posit-connect-cloud

The first run opens a browser to sign in, then uploads the site.

quarto publish renders the project first by default. Add --no-render to upload the existing _site/.

Extending Quarto

Extensions add features that Quarto does not include by default: shortcodes, filters, custom formats, and revealjs plugins.

quarto add quarto-ext/fontawesome           # icon shortcodes
quarto use template quarto-journals/plos    # start an article in a journal format

They install into _extensions/ next to _quarto.yml, so they belong to the project, not to your machine. Commit the folder, as you do _freeze/, so other contributors use the same extensions when they render the project.

Learn more: Quarto extension listing · m.canouil.dev/quarto-extensions (a searchable, community-maintained catalog)

  • Say: “Before you write a Lua filter, look in the listings. Someone has probably done it.”
